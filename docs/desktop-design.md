# Deberopa Desktop 설계서

- 작성: 2026-10-14, 초안 0.1
- 상태: **결정 반영본**(2026-10-14). 15절의 결정이 확정되었다. 구현은 D0 스파이크부터 시작한다.
- 대상: `nxodh/deberopa` (현재 0.2.0: 터미널 에이전트, HTTP 서버, ACP, VS Code 확장)
- 이 문서는 법률 자문이 아니다. 2절의 판단은 공개된 라이선스 문구를 읽은 결과이며, 배포 전에 소유자가 확인해야 한다.

## 0. 한 장 요약

| 항목 | 결정(제안) |
|---|---|
| 제품 | **Deberopa Desktop**: 에디터, 에이전트 대화, 터미널, 파일, diff를 한 창에 담은 데스크톱 앱 |
| 에디터 기반 | **Code - OSS(MIT) 소스를 직접 빌드**한 에디터. Microsoft가 배포하는 "Visual Studio Code" 바이너리와 로고, 마켓플레이스는 쓰지 않는다 |
| 에이전트 | 기존 `deberopa` 실행 파일을 앱에 **그대로 동봉**하고 `deberopa serve`(HTTP + SSE)를 자식 프로세스로 띄운다. 화면은 그 API의 얇은 클라이언트다 |
| 기능 동등성 | 로직을 앱에 다시 만들지 않는다. 모든 기능은 서버 API 한 곳에 있고, 터미널 UI와 같은 세션 저장소를 공유한다. 통합 터미널에서 `deberopa`도 그대로 실행된다 |
| 글꼴 | **Pretendard**(SIL OFL 1.1: 동봉·재배포 가능). 코드 영역은 고정폭 글꼴이 필요하므로 별도(11.3절, 결정 필요) |
| 색 | 로고에서 뽑은 무채색 두 값(`#F0F0F0`, `#040404`)과 그 사이의 회색 단계. 색조가 있는 색은 의미 표시(오류, diff)에 한해 채도 낮은 2색만 기본으로 쓰고 무채색 모드로 끌 수 있다 |
| 모양 | 곡률이 있는 사각형이 기본(반지름 6/10/14/20). 각진 사각형은 구분선과 표처럼 구조상 필요한 곳에만 |
| 플랫폼 | **Debian 13 기반 Linux(Opereta OS 포함)와 Windows 11, x86-64만.** macOS와 ARM은 지원하지 않는다(2026-10-14 결정) |
| 서명·배포 | 비용 0, 법적 문제 없는 방식: 체크섬 + 빌드 증명 + 앱이 검증하는 업데이트 서명, Windows는 SignPath Foundation의 무료 오픈 소스 서명을 신청(8.4절) |
| 확장 | **Open VSX를 기본으로 쓰지 않는다**(결정 2026-10-14). Code - OSS 내장 확장 + **Deberopa 카탈로그**(CI가 만드는 정적 색인과 VSIX, GitHub 무료 호스팅, 로컬 검색·설치·업데이트 알림) + VSIX 직접 설치. 비용 0, 3.1절 |
| 릴리스 | **Deberopa(CLI)와 Desktop을 함께 올린다.** 같은 버전 번호, 같은 태그, 한 번에 검증(10.4절) |

## 1. 목표와 비목표

### 목표

1. 터미널을 쓰지 않는 사람도 Deberopa를 설치해서 바로 쓸 수 있다(접근성).
2. 현재 Deberopa의 **모든 기능**이 앱에서 되거나, 되지 않는 것은 5절의 표에 이유와 대체 경로가 적혀 있다.
3. 에디터는 VS Code와 같은 사용감(키 바인딩, 확장, 설정 형식)을 유지한다.
4. 지원 플랫폼(Debian 13 기반 Linux, Windows 11)에서 같은 기능, 같은 모양.
5. 사용자의 코드와 대화는 기기를 떠나지 않는다(텔레메트리 없음, 대화 업로드 없음. 기존 방침과 같다).

### 비목표

- Microsoft 마켓플레이스와 Microsoft 독점 확장(C/C++, C#, Pylance, Remote 계열, Live Share, Copilot)의 지원.
- 새 에이전트 로직. 에이전트의 동작은 CLI와 앱에서 항상 같아야 한다.
- 모바일, 웹 호스팅 버전.
- 구독 계정 OAuth(`docs/oauth-policy.md`의 결정 유지).

## 2. 법적 검토

### 2.1 VS Code를 기반으로 해도 되는가

| 사실 | 근거 | 결론 |
|---|---|---|
| `microsoft/vscode` 저장소의 소스는 **MIT**(Copyright Microsoft Corporation) | [LICENSE.txt](https://raw.githubusercontent.com/microsoft/vscode/main/LICENSE.txt) | 소스를 받아 수정하고 재배포해도 된다. 라이선스 문구와 저작권 표시를 유지한다 |
| Microsoft가 배포하는 "Visual Studio Code"는 **별도의 Microsoft 제품 라이선스**이며 제3자의 재배포, 독립 제품으로의 제공을 금지한다("share, publish, rent or lease the software, or provide the software as a stand-alone offering") | [VS Code License](https://code.visualstudio.com/license) | **Microsoft 바이너리를 앱에 넣어 배포할 수 없다.** 소스에서 직접 빌드한다 |
| 상표(이름, 로고)와 텔레메트리 키, 업데이트 서버 주소는 배포판의 `product.json`에만 있고 저장소 빌드에는 없다 | [Differences between the repository and Visual Studio Code](https://github.com/microsoft/vscode/wiki/Differences-between-the-repository-and-Visual-Studio-Code) | 직접 빌드하면 "Microsoft 사용자 지정 없는" 빌드가 된다. 이름, 아이콘, 업데이트 주소는 우리 것을 넣는다 |
| 마켓플레이스는 약관상 "Visual Studio 제품과 서비스"에서만 쓸 수 있다 | [VSCodium 문서의 인용](https://github.com/VSCodium/vscodium), [Eclipse 관련 보도](https://newsroom.eclipse.org/node/38074) | **마켓플레이스를 쓰지 않는다.** 확장 갤러리는 Open VSX를 쓴다 |
| 일부 확장과 원격 개발 서버 구성요소는 "Visual Studio family 제품 전용" 라이선스이며, 네이티브 모듈이 VS Code인지 확인한다 | 위 wiki 문서 | 해당 확장은 앱에서 동작하지 않는다고 문서에 명시하고, 대체 확장을 안내한다(6.4절) |

결론: **"VS Code 기반"은 가능하다. 단, 기반은 Code - OSS 소스이지 Microsoft가 배포하는 VS Code가 아니다.**
VSCodium이 같은 방식(소스 빌드, 텔레메트리 제거, Open VSX)으로 MIT 바이너리를 배포하고 있다.

지켜야 할 것:

- 제품 이름과 아이콘에 "Visual Studio Code", "VS Code", Microsoft 로고를 쓰지 않는다. 설명 문장에서 "VS Code 확장과 호환된다", "Code - OSS를 기반으로 한다"처럼 사실을 서술하는 것은 허용되는 범위라고 판단하나, 문구는 배포 전에 확인한다.
- Microsoft 독점 확장의 VSIX를 번들하지 않는다.
- Open VSX는 **기본 확장 공급처로 쓰지 않기로 했다**(3.1절). 이용 조건은 참고용으로 2.4절에 남긴다.
- 소스의 MIT 고지, 그리고 포함되는 서드파티 고지(`ThirdPartyNotices`)를 앱의 "정보" 화면과 설치본에 포함한다.

### 2.2 Pretendard를 전체에 써도 되는가

| 사실 | 근거 |
|---|---|
| 라이선스는 **SIL Open Font License 1.1**, 저작권 Kil Hyung-jin(2021). Reserved Font Name은 "Pretendard" | [LICENSE](https://raw.githubusercontent.com/orioncactus/pretendard/main/LICENSE) |
| 소프트웨어에 **동봉(bundle), 포함(embed), 재배포가 허용**된다 | 같은 문서 |
| 글꼴을 **단독으로 판매**할 수 없다(소프트웨어에 포함해 판매하는 것은 된다) | 같은 문서 |
| **수정본은 "Pretendard"라는 이름을 쓸 수 없다** | 같은 문서 |

결론: **법적으로 문제없이 앱 전체에 적용할 수 있다.** 조건:

1. 글꼴 파일은 프로젝트가 배포한 **원본 파일을 수정하지 않고** 넣는다. 일부 글자만 남기는 서브셋 등은 수정에 해당할 수 있으므로, 서브셋을 만들 경우 이름을 바꾸거나 OFL FAQ를 확인한다.
2. 라이선스 전문과 저작권 표시를 앱에 포함하고 "정보" 화면에 노출한다(`assets/fonts/Pretendard/OFL.txt`).
3. Pretendard는 비례폭 글꼴이다. **코드 편집기와 터미널에는 고정폭 글꼴이 필요**하므로 "프로그램 전체"에서 이 두 영역은 예외다(11.3절).

설계 반영:

1. 갤러리 주소를 설정 값으로 둔다(사용자와 회사가 자체 미러로 바꿀 수 있음).
2. 앱이 확장 목록과 메타데이터를 **캐시**하고, 자동 업데이트 확인의 빈도를 낮춘다(새로 설치할 때와 사용자가 연 화면에서만 요청).
3. 기본으로 쓸 만한 확장(언어 기능, 테마)은 라이선스가 허용하는 범위에서 **설치본에 번들**해 첫 실행의 요청을 줄인다.
4. 사용자가 많아지기 전에 Eclipse Foundation의 인프라 팀(연락처는 위 사용 한도 안내 페이지)에 연락한다.

## 3. 기반 기술 선택

| 안 | 내용 | 장점 | 단점 | 판단 |
|---|---|---|---|---|
| **A. Code - OSS 빌드 + 내장 확장** | 소스를 고정 태그로 받아 패치 최소화, 에이전트 UI는 내장 확장으로 | VS Code 사용감과 확장 호환. 에디터, 터미널, diff, 검색, SCM을 새로 만들지 않는다 | 빌드 파이프라인과 서명, 업스트림 병합 부담. 워크벤치 CSS 변경은 패치 필요 | **권고** |
| B. VS Code 확장만 제공 | 현재 `ide/vscode` | 가장 작다 | Microsoft 바이너리를 번들할 수 없으므로 "앱"이 아니다. 사용자가 VS Code를 따로 설치해야 한다 | 이미 있음(유지) |
| C. Electron/Tauri + Monaco(MIT) 직접 구성 | 파일 트리, 터미널, diff를 직접 구현 | 디자인 자유도 최대, 가벼움 | 확장 생태계, 디버거, 설정 UI를 잃는다. "VS Code 기반"이 아니다 | 보류(가벼운 판 후보) |
| D. Eclipse Theia | VS Code 확장 호환 프레임워크(EPL-2.0) | 임베딩에 친화적 | 모양이 VS Code와 다르고 생태계가 작다 | 비선택 |
| E. 에이전트 전용 앱(에디터 없음) | 대화, diff, 터미널만 | 가장 단순 | 요구사항(VS Code 기반 편집기)을 만족하지 않는다 | 비선택 |

권고안 A의 원칙(**얇은 포크**):

1. 업스트림은 **정확한 태그에 고정**하고, 변경은 `patches/*.patch`로만 관리한다(소스 트리를 직접 수정하지 않는다). 패치는 번호와 이유를 적는다.
2. 에이전트 기능은 전부 **내장 확장**(`extensions/deberopa-agent`)으로 만든다. 패치는 브랜딩, 갤러리 주소, 텔레메트리 제거, 워크벤치 모양(8절)에 한정한다.
3. 업스트림 갱신은 분기마다 한 번, CI에서 패치 적용 실패와 스모크 시험으로 막는다.

### 3.1 확장 공급 방식 (Open VSX를 쓰지 않는다)

결정(2026-10-14, 세부는 소유자 위임): 사용자 앱이 외부 레지스트리에 직접 의존하지 않는다. 목표는 **비용 0, 법적 문제 없음, 사용 한도 없음, 기능이 갤러리 방식에 크게 뒤지지 않음**이다.

핵심: **우리가 직접 만드는 정적 카탈로그**를 GitHub(무료)에서 서비스하고, 앱이 그 카탈로그로 검색, 설치, 업데이트 알림을 제공한다.

| 층 | 내용 | 비용 | 법적 성격 |
|---|---|---|---|
| ① 내장 확장 | Code - OSS 소스에 포함된 확장(언어 기본 지원, 테마, Git, Markdown 등)과 우리의 내장 확장 | 0 | MIT. 소스 빌드에 포함 |
| ② **Deberopa 카탈로그** | CI가 만드는 정적 파일 모음: `index.json`(이름, 설명, 분류, 버전, 라이선스, 아이콘, 검색용 토큰, SHA-256)과 확장별 `.vsix`. 위치는 GitHub Releases(VSIX)와 GitHub Pages(색인). 앱의 "확장" 화면이 이 색인을 내려받아 **로컬에서 검색**하고, 설치는 표준 VSIX 설치 명령으로 한다 | 0 (공개 저장소) | 아래 "카탈로그 규칙"을 지킨 확장만 포함 |
| ③ 직접 설치 | "VSIX 파일에서 설치", "GitHub 릴리스 주소로 설치"(해시 확인 후). 카탈로그에 없는 확장은 이 경로 | 0 | 사용자의 선택. 각 확장의 라이선스는 사용자가 지킨다는 안내를 화면에 표시 |
| ④ 사용자 지정 갤러리(선택) | 설정에서 갤러리 주소를 직접 적을 수 있다(Open VSX 포함). **기본은 비어 있다** | 0 | 사용자가 켠 경우의 이용 조건은 그 서비스의 몫 |

#### 카탈로그 규칙

1. **허용 목록 방식**: 카탈로그에는 검토를 통과한 확장만 넣는다. 처음에는 언어 지원, 포매터/린터 연동, 테마, 아이콘, 생산성 확장 등 널리 쓰이는 것 위주로 수십~수백 개로 시작한다.
2. **라이선스 검사**: 확장의 `package.json`과 라이선스 파일로 재배포 가능 여부를 확인한다. 재배포를 허용하는 라이선스(MIT, Apache-2.0, BSD, ISC, MPL-2.0 등)의 확장만 VSIX를 우리 릴리스에 올린다. 그 밖의 라이선스는 목록에 **주소만** 두고(설치는 제작자 릴리스에서 직접), 독점 라이선스와 Microsoft 마켓플레이스 전용 확장은 넣지 않는다.
3. **출처 확인**: CI가 확장 제작자의 공식 릴리스(또는 소스 저장소)에서 VSIX를 내려받아 해시를 기록하고, 업스트림의 새 버전이 나오면 사람이 검토한 뒤 갱신한다(자동 병합 없음). 라이선스 전문과 저작권 표시는 VSIX 안에 그대로 두고 카탈로그 화면에 표시한다.
4. **갱신 비용**: 색인 갱신은 하루 한 번 이하의 CI 작업이다. **사용자 수와 상관없이 외부 레지스트리에 가는 요청이 늘지 않는다.**
5. **요청 경로**: 목록에 없는 확장은 "카탈로그에 추가 요청" 링크(저장소 이슈 양식)를 제공한다.

#### 기능 비교 (갤러리 방식 대비)

| 기능 | 카탈로그 방식 |
|---|---|
| 검색, 분류, 상세 | 지원(로컬 색인 검색) |
| 설치, 제거 | 지원(VSIX 설치 명령) |
| 업데이트 알림과 설치 | 지원(색인의 버전 비교, 사용자 확인 후) |
| 오프라인 | 색인 캐시로 검색 가능, 설치는 내려받은 VSIX만 |
| 평점, 다운로드 수, 추천 | **없음**(갤러리의 서비스 기능) |
| 긴 꼬리 확장(카탈로그 밖) | ③으로 설치 가능하나 검색에는 안 나옴 |
| 확장 서명 검증 | 갤러리 서명 대신 해시와 우리의 서명(8.4절의 minisign 키)으로 검증 |

참고한 대안과 제외한 이유:

- **Open VSX 기본 사용**: 사용 한도와 상업 규모 협의 조항(2.4절)이 제품 규모에 따라 문제가 될 수 있어 제외(④로 사용자가 켤 수는 있음).
- **Open VSX 서버를 직접 운영**: 서버 비용이 든다. 제외.
- **`coder/code-marketplace`를 앱에 내장**: 라이선스가 **AGPL-3.0**이라 MIT 제품에 넣기에 부담이다([저장소](https://github.com/coder/code-marketplace)). 제외.
- **갤러리 API를 흉내 내는 서버**: 정적 카탈로그와 VSIX 설치로 같은 기능을 얻으므로 만들지 않는다.

남은 확인 사항(D0): 대표 확장 열댓 개로 VSIX 설치가 Code - OSS 빌드에서 정상 동작하는지, 확장 서명 검증 설정(`extensions.verifySignature` 계열)과 충돌하는지, 갤러리 메타데이터를 가정하는 확장이 있는지.

## 4. 아키텍처

```
┌──────────────────────── Deberopa Desktop (Electron, Code - OSS 기반) ───────────────────────┐
│  Workbench (에디터 · 파일 · 터미널 · diff · 검색 · SCM)                                       │
│     ▲                                                                                       │
│     │ VS Code Extension API                                                                 │
│  내장 확장 deberopa-agent ── 웹뷰(대화, 세션, 권한, 모델 선택)                                 │
│     │  HTTP + SSE (127.0.0.1:임의 포트, 실행마다 새 암호)                                      │
│     ▼                                                                                       │
│  deberopa serve  (동봉된 실행 파일, 자식 프로세스)                                            │
│     ├─ 세션 저장소  ← 터미널 UI(`deberopa`)와 같은 폴더를 공유                                 │
│     ├─ 도구(bash/read/edit/…), 권한, MCP, LSP, 스냅숏                                         │
│     └─ 제공자(Anthropic, OpenAI 호환, Ollama, Opereta …)                                      │
└─────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 4.1 프로세스와 통신

- 앱은 시작할 때 `deberopa serve --port 0`으로 서버를 띄우고, 실제 포트를 읽어 연결한다. 서버 주소는 loopback에 한정하고 암호(`DEBEROPA_SERVER_PASSWORD`)를 **실행마다 새로 만든다**. 암호는 확장의 호스트 프로세스 메모리에만 있고 디스크에 쓰지 않는다.
- 같은 사용자의 여러 창은 서버 하나를 공유한다(첫 창이 띄우고, 이후 창은 잠금 파일에서 주소를 읽는다). 마지막 창이 닫히면 서버를 끝낸다.
- 서버가 죽으면 확장이 한 번 재시작하고, 진행 중이던 요청은 오류로 표시한다(세션은 디스크에 있으므로 이어 쓸 수 있다).
- 원격 서버 모드: 설정에서 다른 `deberopa serve`(HTTPS + 암호)에 연결할 수 있다. SDK가 이미 원격 연결에 HTTPS를 요구한다.

### 4.2 데이터

- 세션, 로그인, 설정은 CLI와 **같은 폴더**를 쓴다(`~/.config/deberopa/`, 데이터·상태 폴더 포함). 앱과 터미널을 오가도 같은 세션이 보인다.
- 앱 자신의 상태(창 크기, 최근 폴더 등)는 에디터의 사용자 데이터 폴더(`~/.config/Deberopa Desktop` 등 플랫폼 관례)에 둔다. 에이전트 상태와 섞지 않는다.

### 4.3 보안

| 위협 | 대응 |
|---|---|
| 같은 컴퓨터의 다른 프로세스가 서버에 접속 | 실행마다 임의 포트와 암호, Host/Origin 검사(서버에 이미 있음) |
| 웹뷰가 임의 코드를 실행 | `contextIsolation`, `sandbox`, 엄격한 CSP, 외부 리소스 로드 금지. 마크다운은 정화 후 렌더링 |
| 열어 본 저장소의 설정이 명령을 실행 | 프로젝트 신뢰(`deberopa trust`)를 VS Code의 **Workspace Trust와 하나의 대화상자**로 합친다. 신뢰하지 않은 폴더에서는 지금처럼 위험한 설정을 무시한다 |
| 키 노출 | 키는 확장 UI에 다시 표시하지 않는다. 입력은 서버의 인증 저장소(0600)에만 쓴다. 로그와 오류는 기존 `redact`를 거친다 |
| 도구가 파일을 바꾼다 | 기존 권한 모델(`allow/ask/deny`)을 그대로 표시한다. 앱이 자체적으로 "항상 허용"을 만들지 않는다 |
| 업데이트 변조 | 8.4절: 앱에 박힌 공개키로 업데이트 정보와 자산 해시를 검증 |

### 4.4 오프라인과 개인정보

- 텔레메트리, 크래시 업로드, 업데이트 확인 외의 외부 통신이 없다(업데이트 확인은 끌 수 있다).
- 에디터의 원격 자원(확장 갤러리, 설정 동기화, 실험 서비스)은 `product.json`에서 갤러리만 남기고 제거한다.

## 5. 기능 동등성

원칙: **CLI의 모든 기능은 (a) 전용 화면, (b) 명령 팔레트 항목, (c) 통합 터미널에서 `deberopa` 실행 중 하나로 도달 가능**해야 한다. 아래 표는 (a)/(b)를 정한 것이고, 목록에 없는 CLI 하위 명령은 모두 (c)로 항상 가능하다.

| 기능 | Desktop의 자리 | 사용하는 서버 API | 서버 쪽 추가 |
|---|---|---|---|
| 대화, 스트리밍 Markdown, 도구별 보기(명령 출력, todo, 하위 에이전트) | 대화 패널 | `GET /event`, `POST /session/:id/prompt_async`, 메시지 | 없음 |
| diff와 파일 변경 | 에디터의 기본 diff 편집기, 변경 목록 | 메시지의 도구 결과 | 변경 파일 목록 엔드포인트(6절) |
| `@파일` 첨부, `@파일#L10-20`, 이미지 | 입력창 자동 완성, 드래그 앤 드롭, 에디터 선택 영역 보내기 | `GET /find/file` | 줄 범위 첨부 필드 확인 |
| `/명령`, 사용자 명령, 스킬 | 입력창 슬래시 메뉴 | `GET /command`, `POST /session/:id/command` | 스킬 목록 |
| `!셸` 모드 | 입력창 모드 전환 | `POST /session/:id/shell` | 없음 |
| 에이전트 선택(build/plan/…), 사용자 정의 에이전트 | 입력창 상단 선택기, 설정 | `GET /agent` | 에이전트 파일 편집은 에디터로 연다 |
| 모델, 제공자 선택, 로컬 서버 감지 | 모델 선택기, "모델 서버" 화면 | `GET /provider` | 감지 결과와 상태(`debug local`), 사용 가능 여부 |
| `auth login/list/logout` | 로그인 화면(키 입력) | 없음 | **인증 라우트**(키 저장, 삭제, 목록) |
| 권한 요청(`once/always/reject`) | 대화 안의 카드, 알림 | `GET/POST /permission` | 없음 |
| 세션: 목록, 이어가기, 이름 변경, 삭제 | 세션 목록 | `GET/PATCH/DELETE /session` | 없음 |
| 되돌리기/다시 실행, 요약(compact), 포크 | 메시지 메뉴, 명령 팔레트 | `/revert`, `/unrevert`, `/compact`, `/fork` | 스냅숏 경고를 응답에 포함 |
| 내보내기/가져오기, HTML 공유 | 세션 메뉴 | `GET /session/:id/export` | 가져오기, 공유 뷰어 시작 |
| 사용량과 비용(`stats`) | 상태 표시줄, 통계 화면 | 메시지의 사용량 | `stats` 집계 라우트 |
| Git 상태, 브랜치, 변경 수, PR 검토(`deberopa pr`) | 상태 표시줄, SCM 보기와 연동 | `GET /project` | PR 검토 시작 라우트 |
| 프로젝트 신뢰 | Workspace Trust 대화상자와 통합 | 없음 | **신뢰 라우트**(상태 조회, 신뢰, 해제) |
| MCP 서버, LSP 진단, 포매터 | 설정 화면, 문제(Problems) 패널 | `GET /config` | MCP 상태, LSP 설치 동의 흐름 |
| 플러그인(JS/TS, npm) | 설정 화면의 목록, 설치 확인 | 없음 | 플러그인 목록/설치 확인 라우트 |
| 키 바인딩 | VS Code 키 바인딩과 **하나로 통합**(`deberopa.*` 명령) | 없음 | `keybinds` 설정은 앱에서 무시하고 안내 |
| 테마 | 8절의 디자인 시스템(라이트/다크/시스템) | 없음 | 없음 |
| 웹 검색 동의, 웹 가져오기 | 대화 안의 동의 카드 | 권한 | 없음 |
| `options.ca`, `max_concurrency`, Opereta 인식 | 모델 서버 화면(인증서 상태, 지문, 슬롯) | 없음 | `debug local` 결과 라우트 |
| 업그레이드/제거 | 앱 업데이트(8.4절). `deberopa upgrade`는 앱 안에서 비활성 | 없음 | 비활성 플래그 |
| ACP 서버, GitHub Action, SDK | 앱과 무관하게 CLI로 유지 | — | — |

"서버 쪽 추가"가 있는 항목은 **먼저 서버 API로 만들고**, CLI도 같은 구현을 쓰도록 한다. 앱이 서버 내부를 직접 읽는 일은 하지 않는다.

- 기본 배치는 **오른쪽 대화**. 대화 패널은 어디로든 옮길 수 있다(VS Code 뷰 컨테이너).
- **에이전트 모드**(창 우상단 전환): 대화가 중앙을 차지하고, 편집기와 diff는 필요할 때 오른쪽에 열린다. 코드를 직접 보지 않는 사용자를 위한 배치이며 **첫 실행의 기본값이다**(결정 Q4). 한 번의 클릭으로 전환할 수 있고 선택을 기억한다.
- 상태 표시줄은 TUI의 상태 줄과 같은 정보를 쓴다(브랜치, 변경 수, ahead/behind, 모델 서버, 컨텍스트, 토큰).

### 6.2 주요 화면

| 화면 | 내용 |
|---|---|
| 시작 | 최근 폴더, "폴더 열기", 모델 연결 상태. 제공자가 없으면 연결 마법사로 안내 |
| 연결 마법사 | (1) 이 컴퓨터의 서버 자동 감지(Opereta, Ollama, LM Studio, llama.cpp, vLLM) (2) 키 입력(호스팅 API) (3) 직접 주소(HTTPS와 CA 파일 선택, 인증서 지문 표시). 검증을 끄는 선택지는 없다 |
| 대화 | 메시지, 스트리밍, 도구 카드(접기/펼치기), 권한 카드, todo, 하위 에이전트 활동, 되돌리기 지점 |
| 변경 검토 | 이번 턴에서 바뀐 파일 목록 → 에디터 diff. "되돌리기"가 항상 보인다. 스냅숏이 불가능하면 이유를 같이 표시한다(현재 CLI 동작과 같음) |
| 세션 | 검색, 이름 변경, 포크, 내보내기, 삭제 |

| 설정 | 제공자, 권한 규칙, MCP, 플러그인, 신뢰한 프로젝트, 외관. 설정은 `deberopa.json`을 읽고 쓴다(주석과 형식을 보존) |

### 6.3 접근성

- 모든 기능이 키보드로 도달 가능하다. 포커스 링은 항상 보이고, 대비는 WCAG AA 이상으로 한다(회색 단계 선정 시 계산).
- 화면 낭독기 레이블, 움직임 줄이기 설정 존중, 글자 크기 조절(Pretendard는 가변 글꼴이라 굵기 조절도 가능).

## 7. 디자인 시스템

### 7.1 색

로고 이미지에서 측정한 값: 원판 `#F0F0F0`, 도형 `#040404`. 이 두 값이 시스템의 양 끝이다.

| 토큰 | 라이트 | 다크 | 용도 |
|---|---|---|---|
| `ink` | `#040404` | `#F0F0F0` | 본문, 아이콘, 1순위 버튼 배경 |
| `paper` | `#F0F0F0` | `#101010` | 창 배경 |
| `surface` | `#FAFAFA` | `#181818` | 카드, 입력창 |
| `sunken` | `#E6E6E6` | `#0A0A0A` | 편집기 바깥, 눌린 영역 |
| `line` | `#D6D6D6` | `#2A2A2A` | 구분선, 테두리(1px) |
| `muted` | `#6B6B6B` | `#9A9A9A` | 보조 글자 |
| `focus` | `#040404` 2px 링 | `#F0F0F0` 2px 링 | 키보드 포커스 |

- 색조가 있는 색은 의미 표시에만, **채도를 낮춘 두 가지**(오류, diff 추가/삭제)를 기본으로 쓴다(결정 Q6). 설정에서 "완전 무채색 모드"로 끌 수 있다. 어느 모드에서든 기호(`+`, `−`)와 굵기를 함께 표시해 색각 이상 사용자도 구분할 수 있게 한다.
- 회색 단계는 구현 시 대비를 계산해 확정한다(위 표는 출발값).
- 에디터 구문 강조는 회색의 명도 차이와 굵기/기울임으로 구분하는 **무채색 테마**를 기본으로 하고, 사용자가 일반 VS Code 색 테마를 고를 수 있다(설정 형식이 같음).

### 7.2 모양

| 요소 | 반지름 | 비고 |
|---|---|---|
| 창 | 플랫폼 기본 | Windows 11은 시스템 곡률, Linux는 창 관리자에 따름 |
| 큰 패널, 대화 카드 | 20 | 안쪽 여백 16 |
| 입력창, 메뉴, 팝오버 | 14 | |
| 버튼, 탭, 칩 | 10 | 높이 32(촘촘한 모드 28) |
| 작은 칩, 키 표시 | 6 | |
| 완전 둥근 형태 | pill | 상태 점, 토글 |

- 그림자는 한 단계(부드럽고 낮은 불투명도)만 쓰고, 구분은 1px 선과 배경 단계로 한다.
- 간격은 4px 격자. 한 화면에서 서로 다른 반지름이 3종을 넘지 않게 한다.
- **재질**: Windows 11은 Mica(지원되는 빌드에서), Linux는 불투명. Electron 옵션으로 구현하며 구현 시 Windows 빌드별 동작을 확인한다.
- 워크벤치 자체(탭, 사이드바, 패널)의 둥근 모서리는 업스트림 CSS에서 제한적이므로 **패치 대상**이다(3절 원칙 2). 우리가 만드는 웹뷰 화면은 전부 직접 제어한다. 패치의 범위는 15절의 결정과 업스트림 버전에 따라 줄이거나 늘린다.

### 7.3 글꼴

- UI와 웹뷰 전체: **Pretendard Variable**(원본 파일, 앱에 동봉). 대체 글꼴 순서: 시스템 UI 글꼴 → sans-serif.
- 숫자가 정렬되어야 하는 곳(토큰 수, 표)은 글꼴이 지원하는 경우 표 형식 숫자를 켠다(구현 시 확인).
- **코드 편집기와 터미널**: 고정폭 글꼴이 필요하다. **기본은 D2Coding**(한글 폭을 맞춘 글꼴, SIL OFL 1.1, NAVER, 예약 이름 "D2Coding"), **선택지로 JetBrains Mono**(SIL OFL 1.1, 예약 이름 없음)를 번들한다(결정 Q5). 두 글꼴 모두 2026-10-14에 라이선스 본문을 확인했다. Pretendard와 같은 조건으로 원본을 수정하지 않고 넣고 `OFL.txt`를 함께 포함한다. 편집기 글꼴 설정에서 Pretendard를 고를 수도 있다.
- 글꼴 라이선스 전문은 설치본에 포함한다(2.2절).

### 7.4 아이콘과 움직임

- 선형(1.5px) 아이콘 세트 하나만 쓴다. 채움 아이콘은 선택 상태에만 쓴다.
- 움직임은 120–200ms의 위치와 투명도 변화만 쓰고, "움직임 줄이기"가 켜지면 끈다.
- 로고는 원판 형태 그대로 사용한다(앱 아이콘은 둥근 사각 안에 원판을 넣는다. 도형 자체는 변형하지 않는다).

### 8.2 macOS

지원하지 않는다(2026-10-14 결정). 서명 계정과 공증 비용, 별도 빌드와 시험 부담 때문이다. 나중에 추가한다면 D4의 패키징 단계에서 새로 설계한다.

### 8.3 Windows 11

- 빌드: x86-64만(ARM은 지원하지 않는다. 현재 CLI 빌드 대상에도 Windows arm64가 없다).
- 배포: 사용자 단위 설치 프로그램(`.exe`, 관리자 권한 없이 설치). 서명되지 않은 MSIX는 설치할 수 없으므로 MSIX는 쓰지 않는다. 서명 방식은 8.4절.
- 업데이트: 앱 자체 업데이터. 실행 중인 `.exe`는 덮어쓸 수 없으므로 현재 CLI의 `upgrade`와 같은 "이름 바꾸고 교체" 방식을 쓴다.
- 셸: PowerShell과 Git Bash 감지는 CLI의 기존 로직(`detectShell`)을 그대로 쓴다. 통합 터미널 기본 셸은 PowerShell.
- 긴 경로, 줄 끝(CRLF), 한글 경로 시험 항목을 별도로 둔다.

### 8.4 서명과 배포 무결성 (비용 0, 법적 문제 없음)

원칙: **돈이 드는 인증서와 계정을 쓰지 않고**, 사용자가 받은 파일이 우리가 만든 것인지 검증할 수 있게 하며, 신뢰 저장소를 바꾸라고 요구하거나 경고를 우회시키는 방법은 쓰지 않는다.

| 층 | 방식 | 비용 | 비고 |
|---|---|---|---|
| 모든 자산 | `SHA256SUMS`(릴리스 자산) + **GitHub 아티팩트 증명(build provenance)**. 사용자는 `gh attestation verify`로 "이 저장소의 이 워크플로가 만들었다"를 확인한다. **결정: 사용한다**(공개 저장소, 선택적 보강, 서비스에는 영향 없음). 릴리스 워크플로에 `attest` 단계를 더하는 일은 D4에서 CLI 릴리스와 함께 한다 | 0 (공개 저장소; Actions는 공개 저장소의 표준 러너에서 무료) | 증명 기능의 가격은 문서에서 찾지 못했고 과금 항목으로 안내된 곳도 없다. 첫 적용 때 확인 |
| 체크섬 서명 | `SHA256SUMS`에 **minisign(Ed25519) 분리 서명**. 공개키는 저장소와 앱에 포함, 비밀키는 CI의 암호화 비밀로만 보관 | 0 | 키 분실 대비 폐기·교체 절차를 문서화 |
| 앱 업데이트 | 업데이트 정보(JSON)와 자산 해시를 위 공개키로 앱이 직접 검증한다. 검증 실패 시 설치하지 않는다 | 0 | 코드 서명이 없는 Windows에서도 변조를 막는 핵심 |
| Linux | APT 저장소의 `Release` 메타데이터를 GPG로 서명(Opereta의 저장소 키 정책을 따름). `.deb`를 직접 받는 경우는 위 체크섬 서명 | 0 | `.deb` 개별 서명은 관례가 아니다 |
| Windows 1차(출시) | Authenticode 서명 **없음**. SmartScreen이 "알 수 없는 게시자"를 표시할 수 있음을 설치 안내에 쓰고, 체크섬·증명 검증법을 함께 안내한다. `winget` 매니페스트를 제출한다(해시 검증 포함) | 0 | 경고를 줄이려는 편법(웹 표시 제거 유도 등)은 쓰지 않는다 |
| Windows 2차 (**당분간 하지 않음**, 소유자 결정 2026-10-14: 1차만으로 서비스) | **SignPath Foundation**의 무료 오픈 소스 코드 서명 신청은 나중 선택지로 남긴다. 조건: OSI 라이선스(상업적 이중 라이선스 없음), 독점 구성요소 없음, 이미 릴리스된 형태, 서명 담당 팀의 다중 인증, 홈페이지의 "Code signing policy" 섹션, 검증 가능한 자동 빌드, 릴리스마다 승인. 인증서의 게시자는 SignPath Foundation으로 표시된다. 승인은 재단 재량 | 0 | [조건 출처](https://signpath.org/terms). 1차 릴리스 후 신청(이미 릴리스된 프로젝트여야 함) |

쓰지 않는 방식:

- **자체 서명 인증서**: 사용자에게 신뢰 저장소 변경을 요구하게 되고 보안상 나쁘다.
- **Azure Artifact Signing**: 개인은 미국·캐나다만 대상이라는 안내가 있어 소유자에게 해당하지 않을 가능성이 크다(확인 필요).
- **유료 코드 서명 인증서, macOS 공증**: 비용이 들어 제외한다.
- 다른 사람의 인증서나 서명 서비스를 허락 없이 쓰는 일.

**서명 없는 상태(Windows 1차)로 계속 서비스할 때의 한계** (2026-10-14 조사):

- 법적 문제는 없다. 기술적으로도 동작한다.
- SmartScreen은 서명 여부와 파일 해시의 다운로드 이력(평판)을 본다. 서명이 없으면 "Windows의 PC 보호" 경고가 뜨고 사용자가 "추가 정보 → 실행"을 눌러야 한다. 평판은 파일(해시)마다 쌓이므로 **새 빌드마다 0에서 시작**한다.
- **Smart App Control**(Windows 11)이 켜진 PC에서는 클라우드 서비스가 안전 여부를 판단하지 못한 서명 없는 앱을 **차단**한다([Microsoft 안내](https://support.microsoft.com/en-us/topic/what-is-smart-app-control-285ea03d-fa88-4d56-882e-6698afdb7003)). 새로 설치된 PC에서는 대부분 자동으로 켜져 있을 수 있다고 안내한다. 이 경우 사용자가 Smart App Control을 꺼야 한다.
- 따라서 1차만으로 계속 가는 것은 "코드 지식이 없는 사용자의 접근성"이라는 목표와 충돌할 수 있다. **소유자가 이 한계를 알고 1차만으로 서비스하기로 결정했다.** 설치 안내 문서에 Smart App Control과 SmartScreen 대응 방법을 쓴다.

소유자가 해야 할 일: ① minisign 키 쌍을 만들고 비밀키를 CI 비밀에 넣기(제가 키를 만들거나 저장하지 않는다), ② 1차 릴리스 후 SignPath Foundation에 신청서 제출(저장소, 라이선스, 팀 구성, 홈페이지의 서명 정책 문구 필요).

| 연결 | 감지만 된 상태에서 "설정 만들기" 버튼 → `opereta connect deberopa --write --mcp` 실행(사용자 확인 후). 앱이 Opereta의 파일을 직접 쓰지 않는다 |
| 원격 | 다른 컴퓨터의 Opereta: https 주소, CA 파일 선택, 지문 표시, 키는 환경 변수 또는 인증 저장소 |
| 안내 | 인증서 오류의 해결 안내에 `opereta tls ca/status/renew`를 그대로 표시한다(기존 문구 재사용) |
| MCP | `opereta mcp`가 설정에 있으면 "서버 점검" 도구를 대화에서 쓸 수 있다(읽기 전용 기본) |

## 10. 저장소, 빌드, 릴리스

### 10.1 구조

```
deberopa/                      (현재 저장소)
├─ src/ sdk/ ide/ …            기존
└─ desktop/                    신규
   ├─ vscode/                  업스트림 소스(고정 태그. 서브모듈 또는 빌드 시 내려받기)
   ├─ patches/                 번호가 붙은 패치와 이유
   ├─ product.json             이름, 업데이트 주소 — 확장 갤러리 항목 없음, 텔레메트리 항목 없음
   ├─ extensions/deberopa-agent/   내장 확장(MIT, TypeScript)
   ├─ extensions/deberopa-theme/   무채색 테마
   ├─ assets/fonts/Pretendard/     원본 글꼴 + OFL.txt
   ├─ branding/                    아이콘(플랫폼별), 로고
   └─ build/                       플랫폼별 패키징 스크립트(deb, Windows 설치 프로그램)
```

- 저장소는 **하나로 둔다**(`desktop/`). 두 제품을 함께 올리는 방침(10.4절) 때문이며, 별도 저장소로 나누면 같은 변경을 두 곳에 맞춰야 한다.
- 앱 버전은 동봉된 `deberopa` CLI 버전과 **같은 번호**를 쓴다(예: Desktop 0.3.0은 CLI 0.3.0을 동봉한다).

### 10.2 빌드

- CI 행렬: linux-x64(.deb, tar.gz), win32-x64(설치 프로그램, zip). macOS와 ARM은 없다.
- 동봉 CLI는 기존 `script/build.ts`의 산출물을 그대로 쓴다(별도 빌드 경로를 만들지 않는다).
- 산출물 크기는 에디터와 CLI(현재 압축 전 약 90 MB)를 합쳐 수백 MB가 될 수 있다. 설치 크기는 첫 빌드 후 측정한다.
- 서명 비밀(minisign 비밀키, APT 서명 키)은 저장소의 암호화 비밀에만 두고 로그에 남기지 않는다. 비밀 검사 규칙은 기존과 같다.

### 10.3 릴리스 검증

기존 `Verify release` 방식을 확장한다: 새 컨테이너(Debian 13)에서 `.deb` 설치 → 실행 → 헤드리스 스모크 시험, Windows 러너에서 설치 → 실행 → 스모크 시험. 두 경우 모두 체크섬, 서명, 증명 검증을 포함한다.

### 10.4 함께 올리는 방침 (Deberopa와 Desktop)

소유자 방침(2026-10-14): **Deberopa 또는 Deberopa Desktop의 새 버전을 개발할 때 한쪽만 올리고 끝내지 않는다. 가능한 범위에서 서로의 변경을 반영해 동시에 업그레이드한다.**

| 규칙 | 내용 |
|---|---|
| 버전 | 같은 번호, 같은 태그(`vX.Y.Z`). 한 태그가 CLI 자산과 Desktop 자산을 함께 만든다. 한쪽에만 수정이 있어도 둘 다 올린다(패치 버전 포함) |
| 변경의 방향 | CLI에 기능이 생기면 → (필요하면 서버 API) → Desktop 화면과 명령 팔레트 항목. Desktop에 새 동작이 필요하면 로직은 먼저 서버/CLI에 두고 Desktop은 그것을 호출한다(터미널에서도 되게 하기 위함). 한쪽에만 두는 기능은 예외로 기록한다 |
| 동등성 표 | 5절의 표를 `docs/parity.md`로 옮겨 **릴리스마다 갱신**한다. CI는 서버 라우트와 CLI 하위 명령의 목록을 표와 대조해, 표에 없는 새 항목이 있으면 실패한다 |
| 변경 기록 | `CHANGELOG.md`의 각 버전 절에 "Deberopa"와 "Desktop" 항목을 모두 둔다. 한쪽에 해당이 없으면 "해당 없음"과 이유를 적는다 |
| PR | 한 변경이 다른 쪽에 영향을 주면 같은 PR 묶음(또는 연결된 PR)에서 처리한다. PR 설명에 "다른 쪽 영향" 항목을 둔다 |
| 호환 범위 | 앱은 **동봉된 CLI만** 서버로 쓴다. 원격 서버 모드에서는 서버가 `/health`로 알리는 버전과 API 수준을 확인해 최소 요구보다 낮으면 연결을 거절하고 이유를 보여 준다 |
| 검증 | `Verify release`를 확장해 CLI 설치본과 Desktop 설치본을 같은 버전으로 함께 검사한다(10.3절) |
| 예외 | 한쪽이 기한 내에 끝나지 않으면 **릴리스를 보류하는 것이 기본**이다. 소유자가 승인한 경우에 한해, 못 끝난 쪽을 "미반영"으로 목록에 적고 다음 버전에 반드시 넣는다 |
| 외부 보고 | Opereta 쪽에 알리는 릴리스 보고(버전, 체크섬, 설정 형식 변경)에 Desktop 자산의 이름과 체크섬을 함께 적는다 |

이 방침은 Desktop이 만들어지기 전에도 적용된다: 그동안의 CLI 릴리스는 "Desktop에 필요한 서버 API 변경이 있는가"를 PR마다 확인하고, 있으면 5절의 표에 먼저 올린다.

3. 어떤 화면에서도 허용 목록 밖의 색조 색이 나타나지 않는다(무채색 모드).

7. 같은 태그에서 CLI와 Desktop 자산이 함께 나오고, 동등성 표 검사와 두 설치본의 버전 일치 검사가 통과한다(10.4절).

## 14. 확인하지 못한 것

- Open VSX를 기본으로 쓰지 않으므로 한도 수치는 해당 없음(사용자가 직접 켠 경우에만 해당. 2.4절).

- 제안한 고정폭 글꼴 후보들의 라이선스 본문.
- 최신 업스트림에서 워크벤치 모서리 곡률을 바꿀 수 있는 공식 설정의 범위(D0에서 확인).
- Electron의 Mica 옵션의 Windows 빌드별 동작(D3에서 확인).
- GitHub 아티팩트 증명: 공개 저장소는 일반 제공(2024-06)이며 GitHub 문서에서 비용 언급은 찾지 못했다. 비공개 저장소는 Enterprise Cloud가 필요하다는 2차 자료가 있으나 공식 문서로 확인하지 못했다. 우리는 공개 저장소다.
- SignPath Foundation의 승인 가능성(승인은 신청 후에야 알 수 있다).
- Smart App Control이 우리 앱(서명 없음)을 실제로 어떻게 처리하는지, 설치 후 파일 평판이 어떻게 쌓이는지는 실제 Windows 11에서 측정하지 못했다(D0에서 확인).
- 이 설계의 어떤 부분도 구현이나 빌드로 검증하지 않았다.

| 제품 검사 | `check-product.mjs`가 통과: `nameLong`, 갤러리·채팅 에이전트·MS 호스팅 주소 키 없음, Copilot 언급 없음 |
| 패치 규모 | 상류 소스 패치 1개(115줄, 3개 파일) + 디렉터리 1개 제거 + `product.json` 덮어쓰기 + 아이콘 2개 |
| 패키지 시작 | 처음에는 시작하자마자 `builtInExtensionsEnabledWithAutoUpdates is not iterable`로 종료. 키를 지웠기 때문이며, 빈 배열로 바꿔 해결(아래 교훈) |

D0에서 새로 알게 된 것(설계 가정과 달랐던 것):

1. **Code - OSS 1.141은 Copilot Chat 확장(`extensions/copilot`, MIT, 약 1.7 GB의 작업 트리)을 소스 트리에 둔다.** 그리고 `compile`, 개발 의존 디렉터리 목록, 패키징 단계가 이를 전제한다. 제거에는 빌드 스크립트 패치가 필요하다(패치 0001). 코어에는 `@github/copilot-sdk` 의존성이 남아 있다(에이전트 호스트). 이것까지 걷어내려면 `src/vs/platform/agentHost` 쪽 패치가 더 필요하며 **아직 하지 않았다**. 사용자 쪽에서는 `defaultChatAgent`를 지우고 `chat.disableAIFeatures`를 기본으로 켜 내장 채팅 화면이 나타나지 않게 했지만, 코어의 SDK 코드 자체는 산출물에 남아 있다.
2. **필수 배열·객체 키는 지우면 안 된다.** `builtInExtensionsEnabledWithAutoUpdates`는 배열(빈 배열), `trustedExtensionAuthAccess`는 객체(빈 객체)로 둔다. 키를 지우는 방식은 시작 시점에 깨진다. 그래서 산출물을 **실제로 실행**하는 단계를 CI에 넣었다.
3. 기본 `product.json`에는 `extensionsGallery`가 **없다**(Code - OSS 빌드는 갤러리 없이 나온다). Q12 결정과 맞는다. 다만 `webviewContentExternalBaseUrlTemplate`(MS 호스팅 CDN)과 `voiceWsUrl`(MS 음성 서비스) 같은 외부 주소 키가 있어 지웠다.
4. 내장 확장 3개(`js-debug`, `js-debug-companion`, `vscode-js-profile-table`)는 GitHub 릴리스에서 내려받는 MIT 확장이며 `Microsoft`를 게시자로 표기한다.
5. 빌드 전제: `windows-latest` 이미지에서 상류 `preinstall`이 Visual Studio를 찾지 못해 실패했다(지원 목록이 2022/2019). **Windows 작업은 `windows-2022`로 고정**했다. 상류가 이미지 변화를 따라가면 `windows-latest`로 되돌린다.
6. Windows에서 git의 줄바꿈 변환(autocrlf)이 패치를 깨뜨린다. 복제 시 `core.autocrlf=false`로 두고, 패치 파일은 `.gitattributes`로 바이트 그대로 보존한다.
7. 이 Mac의 4 GB 컨테이너(arm64)에서는 `extensions/copilot`의 esbuild가 중단돼(메모리 부족 추정) 완료하지 못했다. x64 CI 러너(16 GB)에서는 문제가 없었다. 로컬 빌드는 신뢰하지 않고 CI를 기준으로 한다.

아직 하지 않은 것: Windows 11 산출물의 실제 실행 확인(CI 단계는 추가함), Smart App Control 측정(실제 Windows 11 PC 필요: 앱이 완성된 뒤 소유자가 설치해 확인), 대표 확장 15개의 VSIX 설치 시험, 코어의 Copilot SDK 제거, 워크벤치 모서리 곡률 공식 설정 조사.
