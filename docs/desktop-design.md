# Deberopa Desktop 설계서

- 작성: 2026-10-14, 초안 0.1
- 상태: **제안**. 아래 15절의 결정이 나오기 전에는 구현을 시작하지 않는다.
- 대상: `nxodh/deberopa` (현재 0.2.0: 터미널 에이전트, HTTP 서버, ACP, VS Code 확장)
- 이 문서는 법률 자문이 아니다. 2절의 판단은 공개된 라이선스 문구를 읽은 결과이며, 배포 전에 소유자가 확인해야 한다.

## 0. 한 장 요약

| 항목 | 결정(제안) |
|---|---|
| 제품 | **Deberopa Desktop**: 에디터, 에이전트 대화, 터미널, 파일, diff를 한 창에 담은 데스크톱 앱 |
| 에디터 기반 | **Code - OSS(MIT) 소스를 직접 빌드**한 에디터. Microsoft가 배포하는 "Visual Studio Code" 바이너리와 로고, 마켓플레이스는 쓰지 않는다 |

| 색 | 로고에서 뽑은 무채색 두 값(`#F0F0F0`, `#040404`)과 그 사이의 회색 단계만 쓴다. 색조가 있는 색은 의미 표시(오류, diff)에 한해 선택 사항 |
| 모양 | 곡률이 있는 사각형이 기본(반지름 6/10/14/20). 각진 사각형은 구분선과 표처럼 구조상 필요한 곳에만 |
| 플랫폼 | Opereta OS(Debian 13), macOS, Windows 11. 같은 소스, 플랫폼별 패키지 |
| 릴리스 | **Deberopa(CLI)와 Desktop을 함께 올린다.** 같은 버전 번호, 같은 태그, 한 번에 검증(10.4절) |

## 1. 목표와 비목표

### 목표

1. 터미널을 쓰지 않는 사람도 Deberopa를 설치해서 바로 쓸 수 있다(접근성).
2. 현재 Deberopa의 **모든 기능**이 앱에서 되거나, 되지 않는 것은 5절의 표에 이유와 대체 경로가 적혀 있다.
3. 에디터는 VS Code와 같은 사용감(키 바인딩, 확장, 설정 형식)을 유지한다.
4. 세 플랫폼에서 같은 기능, 같은 모양.
5. 사용자의 코드와 대화는 기기를 떠나지 않는다(텔레메트리 없음, 대화 업로드 없음. 기존 방침과 같다).

### 비목표

- Microsoft 마켓플레이스와 Microsoft 독점 확장(C/C++, C#, Pylance, Remote 계열, Live Share, Copilot)의 지원.
- 새 에이전트 로직. 에이전트의 동작은 CLI와 앱에서 항상 같아야 한다.
- 모바일, 웹 호스팅 버전.
- 구독 계정 OAuth(`docs/oauth-policy.md`의 결정 유지).

## 2. 법적 검토

### 2.1 VS Code를 기반으로 해도 되는가

| 사실 | 근거 | 결론 |
|---|---|---|
| `microsoft/vscode` 저장소의 소스는 **MIT**(Copyright Microsoft Corporation) | [LICENSE.txt](https://raw.githubusercontent.com/microsoft/vscode/main/LICENSE.txt) | 소스를 받아 수정하고 재배포해도 된다. 라이선스 문구와 저작권 표시를 유지한다 |
| Microsoft가 배포하는 "Visual Studio Code"는 **별도의 Microsoft 제품 라이선스**이며 제3자의 재배포, 독립 제품으로의 제공을 금지한다("share, publish, rent or lease the software, or provide the software as a stand-alone offering") | [VS Code License](https://code.visualstudio.com/license) | **Microsoft 바이너리를 앱에 넣어 배포할 수 없다.** 소스에서 직접 빌드한다 |
| 상표(이름, 로고)와 텔레메트리 키, 업데이트 서버 주소는 배포판의 `product.json`에만 있고 저장소 빌드에는 없다 | [Differences between the repository and Visual Studio Code](https://github.com/microsoft/vscode/wiki/Differences-between-the-repository-and-Visual-Studio-Code) | 직접 빌드하면 "Microsoft 사용자 지정 없는" 빌드가 된다. 이름, 아이콘, 업데이트 주소는 우리 것을 넣는다 |
| 마켓플레이스는 약관상 "Visual Studio 제품과 서비스"에서만 쓸 수 있다 | [VSCodium 문서의 인용](https://github.com/VSCodium/vscodium), [Eclipse 관련 보도](https://newsroom.eclipse.org/node/38074) | **마켓플레이스를 쓰지 않는다.** 확장 갤러리는 Open VSX를 쓴다 |
| 일부 확장과 원격 개발 서버 구성요소는 "Visual Studio family 제품 전용" 라이선스이며, 네이티브 모듈이 VS Code인지 확인한다 | 위 wiki 문서 | 해당 확장은 앱에서 동작하지 않는다고 문서에 명시하고, 대체 확장을 안내한다(6.4절) |

결론: **"VS Code 기반"은 가능하다. 단, 기반은 Code - OSS 소스이지 Microsoft가 배포하는 VS Code가 아니다.**
VSCodium이 같은 방식(소스 빌드, 텔레메트리 제거, Open VSX)으로 MIT 바이너리를 배포하고 있다.

지켜야 할 것:

- 제품 이름과 아이콘에 "Visual Studio Code", "VS Code", Microsoft 로고를 쓰지 않는다. 설명 문장에서 "VS Code 확장과 호환된다", "Code - OSS를 기반으로 한다"처럼 사실을 서술하는 것은 허용되는 범위라고 판단하나, 문구는 배포 전에 확인한다.
- Microsoft 독점 확장의 VSIX를 번들하지 않는다.
- Open VSX 이용 조건은 2.4절에 정리했다. 요약: 개인 사용은 무료이고 제한이 없는 수준이지만, **제품이 레지스트리에 직접 붙는 구조라 사용량 한도(무료 구간 평균 3 RPS 미만)와 상업 규모 사용의 협의 조항이 우리에게 해당할 수 있다.** 설계에 캐시/미러와 갤러리 주소 설정을 넣는다.
- 소스의 MIT 고지, 그리고 포함되는 서드파티 고지(`ThirdPartyNotices`)를 앱의 "정보" 화면과 설치본에 포함한다.

### 2.2 Pretendard를 전체에 써도 되는가

| 사실 | 근거 |
|---|---|
| 라이선스는 **SIL Open Font License 1.1**, 저작권 Kil Hyung-jin(2021). Reserved Font Name은 "Pretendard" | [LICENSE](https://raw.githubusercontent.com/orioncactus/pretendard/main/LICENSE) |
| 소프트웨어에 **동봉(bundle), 포함(embed), 재배포가 허용**된다 | 같은 문서 |
| 글꼴을 **단독으로 판매**할 수 없다(소프트웨어에 포함해 판매하는 것은 된다) | 같은 문서 |
| **수정본은 "Pretendard"라는 이름을 쓸 수 없다** | 같은 문서 |

결론: **법적으로 문제없이 앱 전체에 적용할 수 있다.** 조건:

1. 글꼴 파일은 프로젝트가 배포한 **원본 파일을 수정하지 않고** 넣는다. 일부 글자만 남기는 서브셋 등은 수정에 해당할 수 있으므로, 서브셋을 만들 경우 이름을 바꾸거나 OFL FAQ를 확인한다.
2. 라이선스 전문과 저작권 표시를 앱에 포함하고 "정보" 화면에 노출한다(`assets/fonts/Pretendard/OFL.txt`).
3. Pretendard는 비례폭 글꼴이다. **코드 편집기와 터미널에는 고정폭 글꼴이 필요**하므로 "프로그램 전체"에서 이 두 영역은 예외다(11.3절).

### 2.3 그 밖의 확인 사항

| 항목 | 상태 |
|---|---|
| 이름 "Deberopa"의 상표 충돌 | 조사하지 않았다(Opereta 인계 문서 7절과 같음). 소유자 몫 |
| 로고의 AI 생성 출처와 저작권 귀속 | 불확실. 소유자 몫 |
| 아이콘 세트 | Apple SF Symbols는 쓸 수 없다. 앱에 번들하는 아이콘은 MIT/ISC/Apache 계열(예: Lucide, Phosphor)에서 고르고 라이선스를 `ThirdPartyNotices`에 넣는다 |
| 코드 서명 | macOS Developer ID와 공증, Windows 코드 서명 인증서가 필요하다. 계정과 비용은 소유자 결정(15절) |

### 2.4 Open VSX 이용 조건 (2026-10-14에 본문을 읽은 결과)

주의: 한도 수치가 문서마다 다르다(위키는 75 RPS의 커뮤니티 구간을 언급하는 반면 관리형 약관은 3 RPS 미만을 Free로 적는다). 단계적 도입 중이므로 구현 시점에 다시 확인한다.

설계 반영:

1. 갤러리 주소를 설정 값으로 둔다(사용자와 회사가 자체 미러로 바꿀 수 있음).
2. 앱이 확장 목록과 메타데이터를 **캐시**하고, 자동 업데이트 확인의 빈도를 낮춘다(새로 설치할 때와 사용자가 연 화면에서만 요청).
3. 기본으로 쓸 만한 확장(언어 기능, 테마)은 라이선스가 허용하는 범위에서 **설치본에 번들**해 첫 실행의 요청을 줄인다.
4. 사용자가 많아지기 전에 Eclipse Foundation의 인프라 팀(연락처는 위 사용 한도 안내 페이지)에 연락한다.

## 3. 기반 기술 선택

| 안 | 내용 | 장점 | 단점 | 판단 |
|---|---|---|---|---|
| **A. Code - OSS 빌드 + 내장 확장** | 소스를 고정 태그로 받아 패치 최소화, 에이전트 UI는 내장 확장으로 | VS Code 사용감과 확장 호환. 에디터, 터미널, diff, 검색, SCM을 새로 만들지 않는다 | 빌드 파이프라인과 서명, 업스트림 병합 부담. 워크벤치 CSS 변경은 패치 필요 | **권고** |
| B. VS Code 확장만 제공 | 현재 `ide/vscode` | 가장 작다 | Microsoft 바이너리를 번들할 수 없으므로 "앱"이 아니다. 사용자가 VS Code를 따로 설치해야 한다 | 이미 있음(유지) |
| C. Electron/Tauri + Monaco(MIT) 직접 구성 | 파일 트리, 터미널, diff를 직접 구현 | 디자인 자유도 최대, 가벼움 | 확장 생태계, 디버거, 설정 UI를 잃는다. "VS Code 기반"이 아니다 | 보류(가벼운 판 후보) |
| D. Eclipse Theia | VS Code 확장 호환 프레임워크(EPL-2.0) | 임베딩에 친화적 | 모양이 VS Code와 다르고 생태계가 작다 | 비선택 |
| E. 에이전트 전용 앱(에디터 없음) | 대화, diff, 터미널만 | 가장 단순 | 요구사항(VS Code 기반 편집기)을 만족하지 않는다 | 비선택 |

권고안 A의 원칙(**얇은 포크**):

1. 업스트림은 **정확한 태그에 고정**하고, 변경은 `patches/*.patch`로만 관리한다(소스 트리를 직접 수정하지 않는다). 패치는 번호와 이유를 적는다.
2. 에이전트 기능은 전부 **내장 확장**(`extensions/deberopa-agent`)으로 만든다. 패치는 브랜딩, 갤러리 주소, 텔레메트리 제거, 워크벤치 모양(8절)에 한정한다.
3. 업스트림 갱신은 분기마다 한 번, CI에서 패치 적용 실패와 스모크 시험으로 막는다.


### 4.1 프로세스와 통신

- 앱은 시작할 때 `deberopa serve --port 0`으로 서버를 띄우고, 실제 포트를 읽어 연결한다. 서버 주소는 loopback에 한정하고 암호(`DEBEROPA_SERVER_PASSWORD`)를 **실행마다 새로 만든다**. 암호는 확장의 호스트 프로세스 메모리에만 있고 디스크에 쓰지 않는다.
- 같은 사용자의 여러 창은 서버 하나를 공유한다(첫 창이 띄우고, 이후 창은 잠금 파일에서 주소를 읽는다). 마지막 창이 닫히면 서버를 끝낸다.
- 서버가 죽으면 확장이 한 번 재시작하고, 진행 중이던 요청은 오류로 표시한다(세션은 디스크에 있으므로 이어 쓸 수 있다).
- 원격 서버 모드: 설정에서 다른 `deberopa serve`(HTTPS + 암호)에 연결할 수 있다. SDK가 이미 원격 연결에 HTTPS를 요구한다.

### 4.2 데이터

- 세션, 로그인, 설정은 CLI와 **같은 폴더**를 쓴다(`~/.config/deberopa/`, 데이터·상태 폴더 포함). 앱과 터미널을 오가도 같은 세션이 보인다.
- 앱 자신의 상태(창 크기, 최근 폴더 등)는 에디터의 사용자 데이터 폴더(`~/.config/Deberopa Desktop` 등 플랫폼 관례)에 둔다. 에이전트 상태와 섞지 않는다.

### 4.3 보안

| 위협 | 대응 |
|---|---|
| 같은 컴퓨터의 다른 프로세스가 서버에 접속 | 실행마다 임의 포트와 암호, Host/Origin 검사(서버에 이미 있음) |
| 웹뷰가 임의 코드를 실행 | `contextIsolation`, `sandbox`, 엄격한 CSP, 외부 리소스 로드 금지. 마크다운은 정화 후 렌더링 |
| 열어 본 저장소의 설정이 명령을 실행 | 프로젝트 신뢰(`deberopa trust`)를 VS Code의 **Workspace Trust와 하나의 대화상자**로 합친다. 신뢰하지 않은 폴더에서는 지금처럼 위험한 설정을 무시한다 |
| 키 노출 | 키는 확장 UI에 다시 표시하지 않는다. 입력은 서버의 인증 저장소(0600)에만 쓴다. 로그와 오류는 기존 `redact`를 거친다 |
| 도구가 파일을 바꾼다 | 기존 권한 모델(`allow/ask/deny`)을 그대로 표시한다. 앱이 자체적으로 "항상 허용"을 만들지 않는다 |
| 업데이트 변조 | 7.4절: 서명된 패키지, 체크섬 확인 |

### 4.4 오프라인과 개인정보

- 텔레메트리, 크래시 업로드, 업데이트 확인 외의 외부 통신이 없다(업데이트 확인은 끌 수 있다).
- 에디터의 원격 자원(확장 갤러리, 설정 동기화, 실험 서비스)은 `product.json`에서 갤러리만 남기고 제거한다.

## 5. 기능 동등성

| `options.ca`, `max_concurrency`, Opereta 인식 | 모델 서버 화면(인증서 상태, 지문, 슬롯) | 없음 | `debug local` 결과 라우트 |

| ACP 서버, GitHub Action, SDK | 앱과 무관하게 CLI로 유지 | — | — |

"서버 쪽 추가"가 있는 항목은 **먼저 서버 API로 만들고**, CLI도 같은 구현을 쓰도록 한다. 앱이 서버 내부를 직접 읽는 일은 하지 않는다.

## 7. 디자인 시스템

### 7.1 색

로고 이미지에서 측정한 값: 원판 `#F0F0F0`, 도형 `#040404`. 이 두 값이 시스템의 양 끝이다.

| 토큰 | 라이트 | 다크 | 용도 |
|---|---|---|---|
| `ink` | `#040404` | `#F0F0F0` | 본문, 아이콘, 1순위 버튼 배경 |
| `paper` | `#F0F0F0` | `#101010` | 창 배경 |
| `surface` | `#FAFAFA` | `#181818` | 카드, 입력창 |
| `sunken` | `#E6E6E6` | `#0A0A0A` | 편집기 바깥, 눌린 영역 |
| `line` | `#D6D6D6` | `#2A2A2A` | 구분선, 테두리(1px) |
| `muted` | `#6B6B6B` | `#9A9A9A` | 보조 글자 |
| `focus` | `#040404` 2px 링 | `#F0F0F0` 2px 링 | 키보드 포커스 |

- 색조가 있는 색은 **기본으로 쓰지 않는다**. 선택 가능한 "의미 색"은 두 가지만 두고(오류, diff 추가/삭제), 채도를 낮춘 값으로 하며 무채색 모드로 끌 수 있다. 무채색 모드에서는 기호(`+`, `−`)와 굵기, 배경 농도로 구분한다.
- 회색 단계는 구현 시 대비를 계산해 확정한다(위 표는 출발값).
- 에디터 구문 강조는 회색의 명도 차이와 굵기/기울임으로 구분하는 **무채색 테마**를 기본으로 하고, 사용자가 일반 VS Code 색 테마를 고를 수 있다(설정 형식이 같음).

### 7.2 모양

| 요소 | 반지름 | 비고 |
|---|---|---|
| 창 | 플랫폼 기본 | macOS는 시스템 곡률, Windows 11은 시스템 곡률 |
| 큰 패널, 대화 카드 | 20 | 안쪽 여백 16 |
| 입력창, 메뉴, 팝오버 | 14 | |
| 버튼, 탭, 칩 | 10 | 높이 32(촘촘한 모드 28) |
| 작은 칩, 키 표시 | 6 | |
| 완전 둥근 형태 | pill | 상태 점, 토글 |

- 그림자는 한 단계(부드럽고 낮은 불투명도)만 쓰고, 구분은 1px 선과 배경 단계로 한다.
- 간격은 4px 격자. 한 화면에서 서로 다른 반지름이 3종을 넘지 않게 한다.
- **재질**: macOS는 사이드바에 시스템 반투명(vibrancy), Windows 11은 Mica(지원되는 빌드에서). Linux는 불투명으로 대체한다. 모두 Electron 옵션으로 구현하며 구현 시 각 플랫폼 버전별 동작을 확인한다.
- 워크벤치 자체(탭, 사이드바, 패널)의 둥근 모서리는 업스트림 CSS에서 제한적이므로 **패치 대상**이다(3절 원칙 2). 우리가 만드는 웹뷰 화면은 전부 직접 제어한다. 패치의 범위는 15절의 결정과 업스트림 버전에 따라 줄이거나 늘린다.

### 7.3 글꼴

- UI와 웹뷰 전체: **Pretendard Variable**(원본 파일, 앱에 동봉). 대체 글꼴 순서: 시스템 UI 글꼴 → sans-serif.
- 숫자가 정렬되어야 하는 곳(토큰 수, 표)은 글꼴이 지원하는 경우 표 형식 숫자를 켠다(구현 시 확인).
- **코드 편집기와 터미널**: 고정폭 글꼴이 필요하다. 후보는 OFL 계열의 JetBrains Mono, D2Coding(한글 폭 맞춤)이며, 둘 다 라이선스 본문을 확인한 뒤 확정한다(15절). 한글 주석이 많은 사용자를 위해 편집기 글꼴 설정에서 Pretendard를 고를 수는 있게 두되 기본값은 고정폭이다.
- 글꼴 라이선스 전문은 설치본에 포함한다(2.2절).

### 7.4 아이콘과 움직임

- 선형(1.5px) 아이콘 세트 하나만 쓴다. 채움 아이콘은 선택 상태에만 쓴다.
- 움직임은 120–200ms의 위치와 투명도 변화만 쓰고, "움직임 줄이기"가 켜지면 끈다.
- 로고는 원판 형태 그대로 사용한다(앱 아이콘은 macOS 규격의 둥근 사각 안에 원판을 넣는다. 도형 자체는 변형하지 않는다).

## 8. 플랫폼별

### 8.1 Opereta OS (Debian 13 기반)

| 항목 | 설계 |
|---|---|
| 패키지 | `.deb`(x86-64 우선, arm64는 15절 결정). Opereta의 APT 저장소에서 배포하고, 설치 경로는 `/opt/deberopa-desktop`, 실행 파일 링크 `/usr/bin/deberopa-desktop`. 동봉된 `deberopa` 실행 파일은 `/opt/…/resources/bin/deberopa` |
| 샌드박스 | Debian 13에서는 AppArmor가 비특권 사용자 네임스페이스를 제한하는 환경이 있어 Chromium 계열 앱이 실행에 실패할 수 있다([관련 보고](https://lists.ubuntu.com/archives/ubuntu-mozillateam-bugs/2024-October/180500.html)). 패키지에 **앱 전용 AppArmor 프로파일**을 넣어 해당 실행 파일에만 `userns`를 허용하고, 샌드박스를 끄는 옵션(`--no-sandbox`)은 쓰지 않는다. Opereta 이미지에서 실제로 확인한다 |
| 업데이트 | Opereta의 업데이트로만 갱신한다. 앱의 자체 업데이트와 동봉 CLI의 `upgrade`는 꺼 둔다(현재 `opereta-vedecaps` 패키지와 같은 방식) |
| 연동 | 이 컴퓨터의 Opereta 서버를 설정 없이 감지(키 불필요, `local_no_key`). `opereta connect deberopa --write --mcp`가 만든 설정을 읽는다. 9절 |
| 화면 서버 | Wayland와 X11 모두. 고해상도와 분수 배율 확인 |
| 파일 연결 | `.desktop` 항목, 폴더에서 "Deberopa로 열기" |

### 8.2 macOS

- 빌드: arm64와 x86-64(유니버설 또는 별도 빌드는 15절). 최소 버전은 업스트림 Electron이 지원하는 범위를 따른다.
- 배포: Developer ID 서명과 공증을 거친 `.dmg`. 공증이 되지 않으면 사용자에게 Gatekeeper 경고가 뜬다.
- 동봉 CLI도 같이 서명한다(공증은 번들 안의 모든 실행 파일을 본다).
- 업데이트: 앱 자체 업데이터(서명된 zip과 체크섬). 동봉 CLI는 앱과 함께 갱신된다.
- 메뉴 막대, 단축키(⌘), 전체 화면, 트랙패드 제스처는 업스트림 동작을 따른다.

### 8.3 Windows 11

- 빌드: x86-64. (현재 CLI 빌드 대상에 Windows arm64가 없으므로 arm64는 이번 범위 밖이다.)
- 배포: 사용자 단위 설치 프로그램(관리자 권한 없이 설치). 코드 서명이 없으면 SmartScreen 경고가 뜬다.
- 업데이트: 앱 자체 업데이터. 실행 중인 `.exe`는 덮어쓸 수 없으므로 현재 CLI의 `upgrade`와 같은 "이름 바꾸고 교체" 방식을 쓴다.
- 셸: PowerShell과 Git Bash 감지는 CLI의 기존 로직(`detectShell`)을 그대로 쓴다. 통합 터미널 기본 셸은 PowerShell.
- 긴 경로, 줄 끝(CRLF), 한글 경로 시험 항목을 별도로 둔다.

## 9. Opereta 연동

| 기능 | 내용 |
|---|---|
| 감지 | `/opereta/info`와 `X-Opereta`로 서버를 알아보고 버전, 슬롯, 요청당 컨텍스트를 상태 표시줄과 "모델 서버" 화면에 보여 준다(0.2.0의 `debug local`과 같은 정보) |
| 연결 | 감지만 된 상태에서 "설정 만들기" 버튼 → `opereta connect deberopa --write --mcp` 실행(사용자 확인 후). 앱이 Opereta의 파일을 직접 쓰지 않는다 |
| 원격 | 다른 컴퓨터의 Opereta: https 주소, CA 파일 선택, 지문 표시, 키는 환경 변수 또는 인증 저장소 |
| 안내 | 인증서 오류의 해결 안내에 `opereta tls ca/status/renew`를 그대로 표시한다(기존 문구 재사용) |
| MCP | `opereta mcp`가 설정에 있으면 "서버 점검" 도구를 대화에서 쓸 수 있다(읽기 전용 기본) |

## 10. 저장소, 빌드, 릴리스

### 10.1 구조

```
deberopa/                      (현재 저장소)
├─ src/ sdk/ ide/ …            기존
└─ desktop/                    신규
   ├─ vscode/                  업스트림 소스(고정 태그. 서브모듈 또는 빌드 시 내려받기)
   ├─ patches/                 번호가 붙은 패치와 이유
   ├─ product.json             이름, 갤러리(Open VSX), 업데이트 주소 — 텔레메트리 항목 없음
   ├─ extensions/deberopa-agent/   내장 확장(MIT, TypeScript)
   ├─ extensions/deberopa-theme/   무채색 테마
   ├─ assets/fonts/Pretendard/     원본 글꼴 + OFL.txt
   ├─ branding/                    아이콘(플랫폼별), 로고
   └─ build/                       플랫폼별 패키징 스크립트(deb, dmg, 설치 프로그램)
```

- 저장소는 **하나로 둔다**(`desktop/`). 두 제품을 함께 올리는 방침(10.4절) 때문이며, 별도 저장소로 나누면 같은 변경을 두 곳에 맞춰야 한다.
- 앱 버전은 동봉된 `deberopa` CLI 버전과 **같은 번호**를 쓴다(예: Desktop 0.3.0은 CLI 0.3.0을 동봉한다).

### 10.2 빌드

- CI 행렬: linux-x64(.deb, tar.gz), darwin-arm64/x64(.dmg), win32-x64(설치 프로그램, zip).
- 동봉 CLI는 기존 `script/build.ts`의 산출물을 그대로 쓴다(별도 빌드 경로를 만들지 않는다).
- 산출물 크기는 에디터와 CLI(현재 압축 전 약 90 MB)를 합쳐 수백 MB가 될 수 있다. 설치 크기는 첫 빌드 후 측정한다.
- 서명 비밀(인증서, 공증 계정)은 저장소 비밀 저장소에만 두고 로그에 남기지 않는다. 비밀 검사 규칙은 기존과 같다.

### 10.3 릴리스 검증

기존 `Verify release` 방식을 확장한다: 새 컨테이너(Debian 13)에서 `.deb` 설치 → 실행 → 헤드리스 스모크 시험, macOS와 Windows 러너에서 설치 → 실행 → 스모크 시험.

### 10.4 함께 올리는 방침 (Deberopa와 Desktop)

소유자 방침(2026-10-14): **Deberopa 또는 Deberopa Desktop의 새 버전을 개발할 때 한쪽만 올리고 끝내지 않는다. 가능한 범위에서 서로의 변경을 반영해 동시에 업그레이드한다.**

| 규칙 | 내용 |
|---|---|
| 버전 | 같은 번호, 같은 태그(`vX.Y.Z`). 한 태그가 CLI 자산과 Desktop 자산을 함께 만든다. 한쪽에만 수정이 있어도 둘 다 올린다(패치 버전 포함) |
| 변경의 방향 | CLI에 기능이 생기면 → (필요하면 서버 API) → Desktop 화면과 명령 팔레트 항목. Desktop에 새 동작이 필요하면 로직은 먼저 서버/CLI에 두고 Desktop은 그것을 호출한다(터미널에서도 되게 하기 위함). 한쪽에만 두는 기능은 예외로 기록한다 |
| 동등성 표 | 5절의 표를 `docs/parity.md`로 옮겨 **릴리스마다 갱신**한다. CI는 서버 라우트와 CLI 하위 명령의 목록을 표와 대조해, 표에 없는 새 항목이 있으면 실패한다 |
| 변경 기록 | `CHANGELOG.md`의 각 버전 절에 "Deberopa"와 "Desktop" 항목을 모두 둔다. 한쪽에 해당이 없으면 "해당 없음"과 이유를 적는다 |
| PR | 한 변경이 다른 쪽에 영향을 주면 같은 PR 묶음(또는 연결된 PR)에서 처리한다. PR 설명에 "다른 쪽 영향" 항목을 둔다 |
| 호환 범위 | 앱은 **동봉된 CLI만** 서버로 쓴다. 원격 서버 모드에서는 서버가 `/health`로 알리는 버전과 API 수준을 확인해 최소 요구보다 낮으면 연결을 거절하고 이유를 보여 준다 |
| 검증 | `Verify release`를 확장해 CLI 설치본과 Desktop 설치본을 같은 버전으로 함께 검사한다(10.3절) |
| 예외 | 한쪽이 기한 내에 끝나지 않으면 **릴리스를 보류하는 것이 기본**이다. 소유자가 승인한 경우에 한해, 못 끝난 쪽을 "미반영"으로 목록에 적고 다음 버전에 반드시 넣는다 |
| 외부 보고 | Opereta 쪽에 알리는 릴리스 보고(버전, 체크섬, 설정 형식 변경)에 Desktop 자산의 이름과 체크섬을 함께 적는다 |

이 방침은 Desktop이 만들어지기 전에도 적용된다: 그동안의 CLI 릴리스는 "Desktop에 필요한 서버 API 변경이 있는가"를 PR마다 확인하고, 있으면 5절의 표에 먼저 올린다.

## 11. 시험과 수용 기준

### 11.1 시험

| 층 | 내용 |
|---|---|
| 단위 | 서버 API 추가분(기존 `bun test` 방식, 모의 모델 서버 재사용) |
| 확장 | 웹뷰 상태 관리, 이벤트 처리, 권한 카드, IME 입력 |
| 통합 | 앱을 띄워 모의 모델 서버에 붙여 "대화 → 도구 → 권한 → 되돌리기"를 끝까지 |
| 동등성 | 5절의 표의 각 행을 CLI와 앱에서 같은 입력으로 실행해 세션 파일의 결과가 같은지 비교 |
| 모양 | 스크린샷 비교(라이트/다크, 세 플랫폼), 반지름과 토큰 위반 검사(허용 목록 밖의 색과 반지름이 있으면 실패) |
| 접근성 | 키보드만으로 5절의 주요 흐름 수행, 대비 계산 |
| 설치 | 세 플랫폼 클린 설치, 업그레이드, 제거. 제거 시 사용자 세션과 설정은 남긴다(옵션으로 삭제) |
| 보안 | 서버 암호 없는 접속 거부, 웹뷰에서 외부 로드 차단, 비밀 검사 |

### 11.2 수용 기준

1. 세 플랫폼에서 클린 설치 후 모델 연결 → 대화 → 파일 수정 → 되돌리기가 동작한다.
2. 5절의 모든 행이 동작하거나 "(c) 통합 터미널"로 도달 가능하다고 문서에 적혀 있다.
3. 어떤 화면에서도 허용 목록 밖의 색조 색이 나타나지 않는다(무채색 모드).
4. 모든 UI 글자가 Pretendard이며(코드 영역 제외), `OFL.txt`가 설치본과 정보 화면에 있다.
5. Microsoft 상표, 로고, 마켓플레이스 주소, 텔레메트리 키가 빌드 산출물에 없다(문자열 검사).
6. 비밀 검사, 타입 검사, 기존 시험이 통과한다.
7. 같은 태그에서 CLI와 Desktop 자산이 함께 나오고, 동등성 표 검사와 두 설치본의 버전 일치 검사가 통과한다(10.4절).

## 14. 확인하지 못한 것

- Open VSX의 한도 수치는 문서마다 달라 구현 시점에 재확인해야 한다(2.4절).
- Pretendard의 서브셋과 웹 글꼴 변환이 OFL의 "수정"에 해당하는지의 세부(원본 파일을 쓰면 해당 없음).
- 제안한 고정폭 글꼴 후보들의 라이선스 본문.
- 최신 업스트림에서 워크벤치 모서리 곡률을 바꿀 수 있는 공식 설정의 범위(D0에서 확인).
- Electron의 Mica/vibrancy 옵션의 플랫폼 버전별 동작(D3에서 확인).
- 이 설계의 어떤 부분도 구현이나 빌드로 검증하지 않았다.
